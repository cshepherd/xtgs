# M9: an 8087 by way of SANE

`XTGS-M9-8087-SANE.md` is the plan: an optional 8087 (`FPU=8087` in
`XTGS.CMD`) whose arithmetic is the IIGS's own SANE tool set, so that a
card whose software patches that tool set is used without XT/GS knowing of
it. This file is what has been found out and what has been built: M9.1,
the look before anything was built; M9.2, the 8087's place in XT/GS; M9.3,
its arithmetic; M9.4, the rest of its instructions; M9.5, its environment
and its exceptions; M9.6, the boot state and the translator. Every
instruction of the 8087's is now done.

## M9.1: is SANE an 8087's arithmetic, and what does it cost

`make sane-spike` (`tools/sane_spike.py`, `tests/sane/sanebench.s`): a
ProDOS 8 system file of its own that starts SANE, runs a table of
operations and keeps what each came back with, then times a loop of each
kind. The tool makes the table, with the result an 8087 gives worked out
in exact arithmetic (Python's fractions, rounded to 64, 53 or 24 bits in
the direction asked for), and judges the bytes. `ZIP=1` times at 16 MHz as
well, `GSOS=1` launches the same file from GS/OS, where System 6 has
patched the tool set. `make sane-basic` is the other side of the
comparison: GW-BASIC's own arithmetic under XT/GS.

All of it is MAME (`apple2gs`: ROM 3). ROM 01 and a real IIGS have not been
tried.

### The interface

From the Apple Numerics Manual (2nd ed., 1988; chapters 11 to 16 and
appendix D), and every line of it borne out by the runs:

- Tool set `$0A`. `SANEStartUp` (`$020A`) takes the address of a page of
  bank `$00` that SANE keeps for itself between calls. `SANEVersion`
  (`$040A`) is `$0300` in ROM 3 and `$0301` under System 6.0.1.
- A call: the source's address (or, for a few, a word by value), the
  destination's address, the opword, `LDX #$090A` (`FP816`) or `#$0B0A`
  (`Elems816`; the manual's note has that number and `DecStr816`'s the
  other way round), `JSL $E10000`. The opword is a format in its high byte
  (extended 0, double 1, single 2, 32-bit integer 3, 16-bit integer 4,
  comp 5) and an operation in its low byte. The destination is extended
  but for the conversions out of it.
- So an 8087's memory operand is SANE's source as it lies in the guest's
  memory: `FADD QWORD PTR [BX]` is one call with the double's address. The
  formats are byte for byte the 8087's (least significant byte first, the
  extended's integer bit explicit), with the differences below.
- What comes back is in X, Y and the flags: a compare's relation (`$40`
  source greater, `$80` less, `$02` equal, `$01` unordered), a classify's
  class and sign, a remainder's seven low bits of the quotient.
- The Environment word is one word: rounding direction in bits 15-14
  (nearest, upward, downward, toward zero), exception flags in 12-8,
  rounding precision in 7-6 (extended, double, single), halt enables in
  4-0. All of an 8087's control word that matters has a place in it but
  the infinity control and the denormal exception.

### Is it right

1,994 operations judged: add, subtract, multiply, divide and square root on
simple and on random operands, in the four rounding directions and the
three precisions; the same with a source that is a double, a single, an
integer of 16, 32 or 64 bits; round and truncate to an integer; every
conversion to and from extended in every direction of rounding; compares.

**1,929 are bit for bit what exact arithmetic says an 8087 gives, the
inexact flag with them. The other 65 are one thing**, and SANE 3.0 and
3.01 both do it: a sum or a difference whose source is *not* extended (a
double, a single, a 16- or 32-bit integer; not a comp) and whose exact
value lies exactly half way between two results comes back as the odd one
of the two, with no inexact flag. It is not rounded at all: the bit that
did not fit is left in the last place. The same operands with an extended
source are right. So an add or subtract of a memory operand is two calls,
the operand made extended first (which is exact) and then the extended
add; multiply and divide by a memory operand are right in one.

What an 8087 does in its own way, and SANE in another (reported by the
tool, not judged):

| | SANE | an 8087 | so |
| --- | --- | --- | --- |
| an exponent field of 0 | 2^-16383 times the significand: `0000 8000000000000000` is 2^-16383, a normalized number | 2^-16382 times it, as an exponent of 1: that pattern is a number the 8087 does not make, and 2^-16383 is `0000 4000000000000000`, a denormal | operands and results with exponent 0 are shifted a bit on the way in and out; a result SANE has there with its last bit set is one the 8087 cannot hold, to be rounded again. Below 2^-16382 only |
| infinity | `7FFF 0000000000000000`; takes either | `7FFF 8000000000000000` | the integer bit set on a result that is one |
| an invalid operation's result | a NaN that says which: `7FFF 4004…` for 0/0, `FFFF 4001…` for a root of a negative | one value, "indefinite": `FFFF C000000000000000` | put in place of SANE's when the invalid flag comes up |
| a quiet NaN operand | carried through as it is, no flag | the same | nothing |
| a signaling NaN operand | made quiet, invalid flagged | the same | nothing |
| 2^63 to a 64-bit integer | `$8000000000000000` and invalid | the same | nothing |
| -2^63 to a 64-bit integer | `$7FFF000000000000`, no flag: wrong | `$8000000000000000` | that one value done by hand |
| `$8000000000000000` from a 64-bit integer | a NaN: it is the comp format's | -2^63 | that one value done by hand |
| a number too large for a 16- or 32-bit integer | `$8000` / `$80000000` and invalid | the same | nothing |
| remainder | the IEEE one: the quotient rounded to nearest (1000.7 rem pi is -1.468, quotient 319) | `FPREM`: the quotient chopped (1.673, quotient 318) | the divisor added back when the sign is not the dividend's, the quotient one less |
| unnormal (integer bit clear, exponent not 0) | taken for its value and normalized | kept unnormal through some operations | to be read in the Intel manual when a program is found that makes one |
| infinities compared | affine: +infinity equals itself, greater than all else | projective by default: the control word's bit chooses | the compare's answer adjusted when the bit says projective |
| an operand that is a denormal | no word about it | its own exception (D) | found by looking at the operand, which costs a test |

The elementary functions are of the 8087's own kind: log2(x), log2(1+x),
2^x-1, tangent and arctangent, the building blocks of `FYL2X`, `FYL2XP1`,
`F2XM1`, `FPTAN` and `FPATAN`. log2(8) is 3 and 2^3-1 is 7 exactly; atan(1)
is pi/4 to the last bit; e^1 is e to the last bit; tan(pi/4) is 1.0 and
ln(e) one unit short of 1. An 8087's own transcendentals are not correctly
rounded either, so these are judged by a tolerance when they are judged.

- **A call costs 750 cycles before it does anything**: the dispatcher and
  SANE's way in and out. An add is under four of those.
- **Multiply, divide and square root are sixteen thousand cycles each.**
  That is where the time of anything that computes will go.
- **The Environment word costs a call to read and a call to set.** Saved
  and put back around every operation, as the plan has it, that is half a
  millisecond on an add of one: the PC keeps SANE's environment as its
  own while it runs, and gives the host's back when it stops.
- **System 6's SANE is a fifth faster than the ROM's.**

### Against arithmetic done by the guest

`make sane-basic`: `tests/sane/fpbase.bas`, loops of one statement under
GW-BASIC (whose numbers are Microsoft's own format, worked by its own
8088 code), each loop timed from MAME by the byte it pokes. The statement
with the operation less the same statement without it, milliseconds at
2.8 MHz:

| | the interpreter | the translator | SANE 3.0 | times as fast |
| --- | ---: | ---: | ---: | ---: |
| add, double | 15.1 | 9.1 | 1.0 | 15, 9 |
| multiply, double | 30.8 | 17.0 | 5.8 | 5.3, 2.9 |
| divide, double | 23.9 | 15.9 | 6.1 | 3.9, 2.6 |
| add / multiply / divide, single | 12.4 / 14.6 / 14.9 | 8.0 / 10.5 / 11.1 | 1.0 / 5.8 / 6.1 | |
| square root (BASIC's is single) | 38.8 | 10.2 | 5.6 | 6.9, 1.8 |
| sine (single) | 190 | 127 | 70 | 2.7, 1.8 |
| logarithm (single) | 78.6 | 52.8 | 89 | 0.9, 0.6 |
| exponential (single) | 80.4 | 52.9 | 70 | 1.1, 0.8 |

BASIC's figure has its own handling of one more operand in it, so the
arithmetic alone is somewhat less; and SANE's is to 64 bits where BASIC's
logarithm is to 24. With that said: **add and subtract an order of
magnitude, multiply and divide three to five times (interpreter) and two
and a half to three (translator), the transcendentals about the same time
for nearly three times the digits.** This is not the comparison the plan
asks for, a compiled program built both ways (Turbo Pascal 5.5's `{$N-}`
and `{$N+}`): there is no such compiler here yet. A program built for an
emulator library pays a trap and a decode for each instruction besides.

### What follows for the design

- An instruction is one call for most forms, two for an add or subtract
  of a memory operand that is not extended, none for the ones that only
  move or change a sign (`FLD ST(i)`, `FXCH`, `FCHS`, `FABS`, the
  constants), which are ten bytes copied.
- Put together from the table, at 2.8 MHz with the ROM's SANE: `FLD
  m64` 0.7 ms, `FSTP m64` 0.9, `FADD ST,ST(i)` 1.0, `FADD m64` 1.8, `FMUL`
  5.8, `FDIV` 6.1, `FSQRT` 5.6, `FCOM` 0.7, `FRNDINT` 0.7, `FPREM` 2.0, and
  XT/GS's own decoding of the instruction on top (a tenth of a
  millisecond, to be measured). `A = B*C + D` is some nine milliseconds.
- If multiply and divide are ever to be faster than SANE's, they are the
  two that could be done here: IEEE says what their result is to the bit,
  so nothing would change but the time, and a card's faster SANE would no
  longer be asked for those two. Not proposed now.
- SANE's page of bank `$00` is one more area for both front ends to
  claim (`src/include/layout.s`).
- Launched from GS/OS, a ProDOS 8 program does not own all of bank `$00`
  below `$BF00`: with results kept up to `$8F00` the system died with
  "Detected trashed memory" (`$0308`, the heartbeat queue) at the point
  where they passed about `$7B00`. The spike keeps less there. XT/GS's own
  loader ends at `$7FFF` and has not met it.

### Gate A

**Correct basic arithmetic and conversions for ordinary finite values:
yes.** Every one of 1,929 is the 8087's to the bit and the 65 that are
not are one behaviour with a plain way round it.

**A performance opportunity: yes for arithmetic, no for
transcendentals.** Against the one software baseline there is, two and a
half times (multiply and divide with the translator) to fifteen (add with
the interpreter); the plan's 1.5 is passed. It is less than was said when
the plan was read: SANE multiplies and divides slowly.

**Go on to M9.2**, with these changes to the plan:

1. The environment is the PC's while it runs (M9.3 has it saved and
   restored at every operation).
2. Add and subtract of a memory operand go by way of an extended
   temporary.
3. An adapter at the edges of the format: exponent 0, infinity's integer
   bit, the indefinite, -2^63, the remainder's sign. Each is a test of a
   few bytes on the way in or out.
4. The 8087 lives in an image and a region of its own, loaded when the
   line is there, as the translator is (SVC has 1.2 KB left and CORE 8),
   and its registers in the results bank, where a boot state already
   keeps them.
5. For the translator, an instruction that stores is the range-checked
   kind of exit (as `REP MOVS`), not "may have written anywhere".

### Not done

- The fixed-work program built with and without the 8087 (no compiler).
- ROM 01, and a real IIGS.
- Exceptions that are not masked: nothing was run with a halt enabled.
  The plan's M9.5.
- The 8087's rules for unnormals and for denormal operands, read only as
  far as their being there. Intel's manual is the authority: *The 8086
  Family User's Manual, Numerics Supplement* (July 1980, order number
  121586-001), which the Internet Archive has
  (`archive.org/details/8086familyusersm00inte`). Apple's is at
  `vintageapple.org/inside_o/pdf/Apple_Numerics_Manual_Second_Edition_1988.pdf`.

## M9.2: its place in XT/GS, its state, its decoder

With M9.2, `FPU=8087` in `XTGS.CMD` was a PC that has an 8087 which
programs find and which computes nothing: its state and the instructions
that set and store it. M9.3 below gives it its arithmetic.

### Where it is

- **The image.** `src/fpu/fpu.s`, the file `FPU` beside `CORE`: an image of
  its own with its relocation list, as the translator's is, in the data
  region's bank (`FPU_BASE`; a PC has no other use for the region that
  holds the vectors under `V`). Both front ends claim that bank for a PC
  (`C`, `D`, `S`) after the translator's and before XMS, load the file
  when it is there, relocate it, and start SANE (`sane_up`) with a page of
  bank `$00` that is theirs: `$1400` for the ProDOS 8 loader, which
  nothing of it or of the PC is in under either layout, and the last page
  of the GS/OS application's block. Without the file the region's word in
  `MB_LAYOUT` is 0 again, which is what the core and SVC go by.
- **The line.** `FPU=8087`; `FPU=OFF` is none, as no line is; any other
  value is none too, and said at the sign-on ("FPU= is 8087 or OFF: no
  coprocessor"), as a line that finds no file is ("FPU=8087: no file FPU,
  no coprocessor"). `rd_readcfg` leaves it in `FPU_CFG`; command `C` reads
  it too. `XTGS_FPU=1` in the environment puts the line and the file on
  any tool's volume (`tools/make_image.sh`), and a volume whose
  `XTGS.CMD` has the line gets the file. The release and the games
  volumes do not have the file (`tools/release_image.py` puts it on only
  for a `--cmd FPU=8087`): until the 8087 has its remaining instructions
  (M9.4, M9.5) and has run on a real IIGS, a volume that is handed out
  does not claim a bank and start SANE for it.
- **The core.** With no 8087 the eight ESC opcodes are what they were:
  the operand decoded, nothing done. `fpu_start`, where a PC starts,
  points them at `fpx_0`-`fpx_7` when `FPU_CFG` is 1 and the image is
  there: the same decoding (`modrm_w`), then `JSL FPU_BASE+3` with the
  opcode's three bits. So a PC without it pays nothing. `WAIT` is a no-op
  with it as without: the 8087 here has done its instruction by the time
  the next one is fetched, and is never busy.
- **The state.** In the results bank (`FPU_*`, `src/include/pc.s`): the
  control, status and tag words, the eight registers, the last
  instruction's pointers, and for a test's sake the count of instructions
  met that are not done (`FPU_BAD`, `FPU_LAST`). So a saved state has all
  of it without a line more, and the table in CORE's bank that
  `fpu_start` changed is in it too: a PC started from a state is not
  given `fp_init`. The image is not in a state; the front end loads it at
  every start. A state is held to it all the same: the build number in
  the state's header counts the 8087's source with CORE's and SVC's, and
  the header's copy of `MB_LAYOUT` has the region's word, so a state
  saved with the file is not used on a volume without it.
- **The BIOS.** Bit 1 of the equipment word (`fp_equip`), which `INT 11h`
  returns.

### What is done

`FNINIT` (and so `FINIT`, which is `WAIT` before it), `FLDCW`, `FNSTCW`,
`FNSTSW` to memory, `FENI`, `FDISI`, `FNCLEX`. The reset is Intel's: control
word `03FFh` (every exception masked, interrupts masked, 64 bits, to
nearest, projective), status 0, every register empty. The control word's
fields, from the manual's figure, for M9.3: rounding in bits 11-10 (00
nearest, 01 down, 10 up, 11 chop: not SANE's order), precision in 9-8 (00
is 24 bits, 10 is 53, 11 is 64), infinity in 12, the interrupt mask in 7.
There is no `FNSTSW AX`: that is the 287's.

Every other instruction is decoded to its length and counted.

### What it owes the rest

- **The translator.** M9.2 had an ESC instruction end a piece and every
  8087 store put the epoch on; M9.6 below changed both.
- **The EGA.** The table that says what each opcode does to an operand in
  the planes (`eg_class`) has the ESC opcodes writing nothing. A store by
  the 8087 into A000 in mode 0Dh is not put through the graphics
  controller, and is lost. Not done until something wants it.

### Tests, and gate B

- `tests/com/fpudet.asm`, run as `fpudet` (with `FPU=8087`) and `fpunone`
  (`FPU=OFF`): the equipment word, `FNINIT` and the two words stored; the
  control instructions; the control word stored through a base and an
  index, a displacement, BP's segment, a segment override and a word
  across the segment's end; and twelve other instructions in every form
  of operand, after which a count says the processor is in step. The

- `make test-fpu` (`tools/fpu_test.py`): Norton Utilities 6.01's System

  are not done, which by `FPU_LAST` are its saving and loading of the

- The CPU's vectors for D8-DF are an 8088 with no coprocessor, and are

**Gate B: met.** A program of the time and a program of the tree's both
tell the two PCs apart; lengths, overrides and the segment's end are

(`XTGS_FPU=1`) and without it.

## M9.3: the arithmetic

The 8087 now computes. What it does, and what it leaves for later:

| | instructions | how |
| --- | --- | --- |
| loads | `FLD` m32/m64/m80/ST(i), `FILD` m16/m32/m64 | here: a conversion into extended is exact, so SANE is not asked |
| stores | `FST`/`FSTP` m32/m64/ST(i), `FSTP` m80, `FIST`/`FISTP` m16/m32, `FISTP` m64 | SANE (`FX2S`, `FX2D`, `FX2I`, `FX2L`, `FX2C`) with the control word's rounding; m80 and a register are copies |
| arithmetic | `FADD`, `FSUB`, `FSUBR`, `FMUL`, `FDIV`, `FDIVR` with m32, m64, ST(i) both ways, the popping forms; `FIADD`... with m16 and m32 | the memory operand made extended here first (which is exact, and is the way round SANE's ties, M9.1), then one SANE call on two extendeds |
| compares | `FCOM`, `FCOMP`, `FCOMPP`, `FICOM`, `FICOMP`, `FTST`, `FXAM` | SANE's `FCMPX` for two numbers; the rest here |
| constants | `FLD1`, `FLDZ`, `FLDPI`, `FLDL2T`, `FLDL2E`, `FLDLG2`, `FLDLN2` | a table, each rounded to nearest |
| the stack | `FXCH`, `FFREE`, `FINCSTP`, `FDECSTP`, `FNOP`, `FCHS`, `FABS` | here |
| rounding | `FRNDINT` | SANE's `FRINTX` |
| control | M9.2's, and `FNCLEX` now SANE's flags too | |

The rest came with M9.4 and M9.5, below. An encoding that is not the
8087's is counted in `FPU_BAD` and does nothing, as in M9.2.

### How

- **The state.** `FPU_SW` is the status word without the stack's top,
  which is `FPU_TOP`; a register is twelve bytes, its ten and its tag, so
  that the tag word is made only when it is asked for (M9.5).
- **SANE's environment is the PC's.** It is set from the control word
  only when an operation needs it otherwise (`fp_need`): rounding and
  precision for arithmetic, rounding alone for a conversion or `FRNDINT`
  (the 8087's precision control has no say in those, and SANE's would).
  So a run of operations under one control word sets it once.
- **SANE's flags stay in SANE** until the status word is wanted (`fp_sw`)
  or the environment is to be set (`fp_fold`): one call, not one an
  operation. Its five flags are the 8087's I, U, O, Z and P.
- **What SANE is never given.** An empty register, a NaN, an infinity, a
  denormal: the 8087's rules for those are here (`fp_arith`, `fp_cmp`,
  from the manual's tables S-26, S-27 and S-32), and SANE gets two
  numbers or nothing. A NaN is returned as it is (of two, the larger
  significand); an empty operand, or a register pushed onto, is the
  indefinite and invalid; infinities follow the control word's infinity
  bit, projective by default, as the manual's table has it.
- **Denormals.** Loaded from a single or a double, a denormal is the
  unnormal of the same value and raises D (table S-24). In a register,
  exponent field 0 is 2^-16382 times the significand on the 8087 and
  2^-16383 in SANE, so a denormal is shifted a place on the way in
  (`fp_dni`) and a result below 2^-16382 on the way out (`fp_dno`), which
  raises U. A denormal divisor is invalid.
- **What SANE returns** is made the 8087's (`fp_post`): its infinity
  without the integer bit gets it, its NaN for an invalid operation
  becomes the indefinite, and under chop an overflow is infinity, which
  is what the 8087 does and IEEE does not (table S-32). The same for a
  store to m32 or m64 under chop.
- **-2^63** to and from a 64-bit integer is done here (M9.1: SANE's comp
  has no such number).
- **The guest's memory.** The core decodes the ModR/M byte as for a byte
  operand (`modrm_b`: no bounce word) and the 8087 reads or writes the
  operand's bytes itself (`fp_get`, `fp_put`), a word at a time, or a
  byte at a time when the operand goes round its segment's end or over a
  bank's. A store marks the text buffer's 256s and puts the translator's
  epoch on.

### Where it is not an 8087

- **Unnormals are not kept.** SANE takes one for its value and returns a
  normal number; the 8087 keeps a result unnormal when an operand was
  (table S-25). Only a program that underflows and goes on computing with
  the result sees it.
- **Precision control** rounds the significand to 24 or 53 bits as the
  8087 does, but SANE also gives the result the single's or the double's
  exponent range, where the 8087 keeps extended's: a result that would
  overflow a double but not an extended is infinity here.
- **A result that underflows inexactly is rounded twice:** by SANE at its
  own last place, then here to the 8087's. An exact one (tested) is right.
- **Compares.** The manual defines C3 and C0 after a compare; C2 is set
  with them for "not comparable", as on the 287, and cleared otherwise.
- **Under chop, an overflow seen after another one** may be taken for
  infinity where the result was the largest number: the test is SANE's
  sticky overflow flag.

### Tests, and gate C

`tests/com/fpuops.asm`, written with its expected output by
`tools/gen_fputest.py`: 168 cases, each a few instructions and then a line
with ST(0) as `FSTP TBYTE` stores it, the status word and the eight bytes
the case stored. **The expected results are not the 8087 code's**: they are

the constants from 70-digit values of pi and the logarithms. The cases:
every arithmetic operation with each memory format and each register
form; the ties SANE gets wrong with a non-extended source; the four
rounding directions on a positive and a negative quotient and the 24- and
53-bit precisions; every compare, `FTST` and `FXAM` on each kind of value,
projective and affine; the constants; the stack instructions; `FRNDINT`
in each direction; stores to every format, in range, out of range and of
the special values, with -2^63; division by zero, 0/0, infinities and
NaNs in arithmetic, the stack's overflow and underflow; denormals in
memory and in a register, exact underflow, a denormal divisor; and a
double and an extended that go round the segment's end.

The first run found one fault in the 8087 code (the class routine left
the compare's flags, so that every integer store was taken for invalid)
and four in the expected values (2^64 - 1 taken for a tie, which it
is not, a NaN's bits shifted by hand, Python's -0.0 that is +0, and the
8087's `FIST` to 64 bits, which does not exist). All 168 match now.

**Gate C: met for the instructions above**, with the differences listed:
arithmetic, the stack, conversions, rounding and the status word against
an independent reference. The instructions left are counted, not
pretended.

## M9.4: the rest of the instructions

| instruction | how |
| --- | --- |
| `FSQRT` | SANE's `FSQRTX`, rounded by the control word. A negative number, a denormal, an unnormal, -infinity, and +infinity when projective, are invalid; +-0 is itself |
| `FSCALE` | SANE's `FSCALBX` by ST(1) chopped to an integer, here; the manual asks for ST(1) between -2^15 and 2^15, and outside that it is taken as +-32767. A denormal ST(1) is 0 |
| `FPREM` | here, exactly: a long division of the significands, 64 bits of quotient at a time. When the exponents are more than 65 apart the remainder is partial and C2 is set, as the 8087 does it, and the program asks again; complete, C0, C3 and C1 are the quotient's last three bits (each partial step leaves at least three bits of difference, so those bits are the whole quotient's) |
| `FXTRACT` | here: the exponent replaces ST, the significand (exponent 3FFFh) is pushed. +-0 gives +-0 twice, as table S-26 has it; infinity is invalid |
| `FBLD`, `FBSTP` | here: eighteen digits and a sign byte. `FBSTP` rounds by the control word (SANE's `FX2C`), and 10^18 and more, infinity, NaN or an empty register store the packed decimal indefinite (FFFF C0 00...) |
| `F2XM1`, `FYL2X`, `FYL2XP1`, `FPTAN`, `FPATAN` | Elems816: 2^x - 1, log2 x (and the product by ST(1) by FP816), log2(1 + x), tan x, arctan(y / x). They raise P and nothing else of SANE's, as the 8087's report only precision |

What is not quite the 8087's:

- **`FPTAN` gives X = 1.** The 8087's answer is a pair Y and X whose
  quotient is the tangent, Y in ST(1) and X in ST; which pair is the
  8087's own. Every program divides them, so here Y is the tangent and X
  is 1, as the 387 has it.
- **Out of the 8087's domains** (`F2XM1` past 0.5, `FPTAN` past pi/4,
  `FPATAN` with X not the larger) the 8087's results are undefined; these
  give the function's value. `FPATAN` puts the angle in its quadrant.
- **The last bits of a transcendental** are SANE's, as the 8087's are its
  own: neither is correctly rounded.
- **Their cost:** 60 to 110 milliseconds each at 2.8 MHz (M9.1's table),
  for 64-bit results; a program that leans on them is slow.

Test: `tests/com/fpuext.asm` (`tools/gen_fputest.py`), 90 cases. The square
root in every direction and at 24 bits, the scale, the extraction, twelve
remainders (one partial four times, one of 2^1000 sixteen times, the
quotient's bits judged), packed decimal both ways with its indefinite, all
against exact arithmetic; and the five transcendentals on sixteen operands,
which the program itself holds to a 70-digit value within 2^-56, with
instructions fpuops judged exactly. The first run differed on two
remainders, and in both the generator was wrong: it had divided the exact
operands, not the ones rounded to 64 bits that the program loads.

## M9.5: the environment and the exceptions

- **The pointers.** Every instruction but the control ones (`FINIT`,
  `FLDCW`, `FSTCW`, `FSTSW`, `FCLEX`, `FENI`, `FDISI`, `FSTENV`,
  `FLDENV`, `FSAVE`, `FRSTOR`) keeps its address, its opcode's eleven
  bits and its memory operand's address, twenty bits each (`fp_begin`).
  The core gives the IP after the opcode (`fpx`); the address is the
  segment prefix's when there is one. The manual does not say which the
  8087 keeps; later chips keep the prefix's, which also lets a handler
  see the override.
- **`FSTENV`, `FLDENV`, `FSAVE`, `FRSTOR`** in the layouts of figures S-19
  and S-18: control, status and tag words, the instruction's address
  (its top four bits above the opcode in the next word), the operand's,
  and for `FSAVE` the registers from ST(0). `FSTENV` then masks every
  exception, `FSAVE` then does `FNINIT`. The tag word is made from the
  registers' tags; loaded, a register the word calls empty is empty, and
  any other is tagged by what it holds (the 8087 may trust the word; a
  program that writes a word that lies about its registers is not one met).
- **An unmasked exception.** The instruction is undone (the registers and
  the stack's top it changed are put back from a log kept while any
  exception is unmasked; a store is not made), the flag is set, and IR
  (bit 7). With the control word's IEM clear the 8087 then asks for its
  interrupt: the core takes INT 2, which is what a PC/XT wires the 8087's
  INT line to (the NMI). IR is set once, until `FNCLEX`, `FNINIT`, or an
  environment loaded without it. `FLDCW`, `FLDENV` and `FRSTOR` that
  unmask a flag already set ask at once, as the manual says. Precision
  is the exception that is not undone: the result stays and the
  interrupt follows.
- **How the exceptions are seen.** SANE is not asked after every
  instruction (a call is 270 microseconds): invalid, zero divide,
  overflow and underflow are seen in the operands and the results, and
  SANE's flags are read only when precision is unmasked, which nothing
  else can tell. Masked, SANE's flags are read only when the status word
  is wanted, and then cleared in SANE.
- **Turbo Pascal 5.5** runs with invalid, zero divide and overflow
  unmasked and IEM clear (control word 1332h), and hooks INT 2 to turn
  the interrupt into its run-time errors 200, 205 and 207. That is the
  path above; it has not been tried with Turbo Pascal itself.

What is not the 8087's:

- **Unmasked overflow and underflow with a register destination:** the
  8087 stores the result with its exponent wrapped by 24,576 and then
  interrupts; here the instruction is undone and interrupts. A handler
  that reads the wrapped result to rescale it gets the operands instead.
- **The NMI mask.** A PC/XT gates the NMI with port A0h; it is not
  modelled, the NMI is always let through. The BIOS sets it open anyway.
- **The busy bit** is always 0: an instruction is done by the time the
  next is fetched. `WAIT` stays a no-op.
- **Timing.** The 8087's interrupt comes some cycles after its
  instruction; here at the next instruction's boundary, so a program
  that races it (none known) sees it early.

Test: `tests/com/fpuenv.asm`, every line of its expected output worked
out by hand from the manual: `FSTENV`'s words and pointers, with and
without a segment prefix, and the control word after it; `FSAVE`'s image
and the reset after it, and `FRSTOR`; `FLDENV`; unmasked invalid, zero
divide, an aborted `FIST` and an unpopped `FISTP`, overflow, precision;
and INT 2 taken once, not taken under `FDISI`, and taken when `FLDCW`
unmasks a flag that is set. The first run differed in one place, and it
was the 8087 code: an out-of-range `FIST` showed precision with invalid,
because SANE flags both; the range of an integer store is now judged
here, after SANE has made a 64-bit integer of the number.

**Gate D: met.** Norton SI, which saves and loads the environment, meets
no instruction that is not done, and Turbo Pascal 5.5's run-time library
finds the 8087 and takes its interrupt (below).



## Turbo Pascal 5.5: the comparison the plan asked for

`python3 -I tools/tp_bench.py TPDIR [--jit] [--zip]`, where TPDIR holds
Turbo Pascal 5.5's `TPC.EXE` and `TURBO.TPL` (its first diskette; not in
the tree). One boot compiles `tests/tp/BENCH.INC` under FreeDOS in XT/GS
twice, `BENCHR` with `{$N-}` (Turbo Pascal's 6-byte `Real`, its own
software arithmetic) and `BENCHD` with `{$N+,E+}` (`Double`: the 8087 when
there is one, Turbo Pascal's emulator when there is not), and
`tests/tp/FPERR.PAS`. Then a boot with `FPU=8087` and one without run
them. The programs time each part by the BIOS's tick count.

- **Detection:** `Test8087` is 1 (an 8087) with the line and 0 without.
  Turbo Pascal tells an 8087 from a 287 by whether +infinity equals
  -infinity after `FINIT` (projective), so that is tested too.
- **The error path:** a division by zero ends in "Runtime error 200" both
  ways; with the 8087, through its interrupt (Turbo Pascal runs with the
  control word 1332h: invalid, zero divide and overflow unmasked, IEM
  clear) and its handler on INT 2.
- **The results:** the `Double` sums are the host's doubles in every
  printed digit, with the 8087 and with the emulator; `Real`'s agree to
  its own precision.

Emulated seconds at 2.8 MHz, the interpreter alone (2026-11-25, MAME):

| part | `Real` | `Double`, Turbo Pascal's emulator | `Double`, the 8087 |
| --- | ---: | ---: | ---: |
| a polynomial, 400 times (multiply and add) | 15.7 | 65.9 | 15.2 |
| 1/i, 400 times (divide) | 12.9 | 16.7 | 3.3 |
| `Sqrt`, 200 times | 34.5 | 10.3 | 2.0 |
| `Sin` and `Exp`, 20 each | 4.1 | 6.1 | 4.0 |
| `Ln` and `ArcTan`, 20 each | 4.8 | 6.3 | 3.4 |
| **all** | **72** | **105** | **28** |

- **A program built for the 8087 runs 3.8 times as fast** with
  `FPU=8087` as it does on the same PC without one (Turbo Pascal's
  emulator), and 2.6 times as fast as the same program built with
  `Real`. The plan's 1.5 is passed.
- **Multiplication is where it does least:** the polynomial is no faster
  than Turbo Pascal's software `Real`, whose 40-bit multiply in 8088 code
  costs about what SANE's 5.8 ms does. Division is four times as fast and
  the square root seventeen.
- **With the translator** (`--jit`) the picture changes: `Real` becomes
  27 seconds (the translator runs Turbo Pascal's arithmetic 2.6 times as
  fast), and the 8087 build stays at 30. An ESC instruction ends a
  translated piece, and every 8087 store into memory turns on the
  translator's watch for code being written over (`inc jEP`), after which
  every piece compares its bytes before it runs. That is M9.6's work: a
  store that is looked at by its address and length, as translated
  stores are, and the 8087 called from translated code.
- **What would make multiplication faster:** SANE's multiply is 16,000
  cycles; a 64-by-64-bit multiply here, sixteen 16-bit products by
  table or shifts and IEEE rounding, might be a third of that, and
  division likewise. Nothing would change but the time, and a card that
  speeds up SANE would no longer be used for those two.

## M9.6: the boot state and the translator

**The boot state** needed little: the 8087's state was put in the results
bank in M9.2, which a state has; the build number counts the 8087's
source; the header's copies of `MB_LAYOUT` and of `XTGS.CMD` hold a state
to the same 8087 and the same line. Two things were added:

- **The image's own view of SANE** (the environment it last set, whether
  SANE has flags it has not read) is not the PC's and is not saved. A PC
  put back without `fp_init`, from a boot state (the core's `fpu_sync`)
  or by the desk accessory's restore (`control.s`), calls the image's
  third entry, `fp_sync`, which forgets it: the next operation sets the
  environment again, which clears SANE's flags.
- **Nothing of the PC's numeric environment outlives it:** both front ends
  set SANE's environment to its default before `SANEShutDown`.

Tested in the four combinations, without and with the 8087 and the
translator: `make test-state` (make, load, go, again), `make
test-control` with both.

**The translator:**

- **ESC is now done inside a piece** (`K_STEP` in `tools/gen_jit.py`):
  the interpreter does the instruction and the piece goes on after it
  (`jit_hook`'s way 3), unless the IP or CS is not the one expected (the
  8087's interrupt) or the epoch has gone on.
- **An 8087 store puts the epoch on only when it lands on a page that
  translated code was made from** (`fp_jep`: the translator gives the
  address of its `pg_map` at `JIT_BASE+3`), which also sends the core
  back to the dispatcher; a store round a segment's or a bank's end, and
  the 8087's interrupt (its frame on the stack), put it on whatever the
  page. `fp_nep` in the image counts the first kind.
- **Tests:** `tools/jit_fuzz.py --micro` has four forms with the 8087 in
  them, one of which has an 8087 store write over the code just ahead of
  it in the same piece; they are no-ops without the 8087 and judged with
  `XTGS_FPU=1`. The micro run plain, small and in the other layout, three
  seeds, `XTGS_JIT=1 make test-com` and `test-share BOOT=1` all pass, and
  the 8087's tests under the translator and both front ends.

**What it bought: nothing measurable, and why.** `tools/tp_bench.py
--jit`, stock speed: `Real` 27.2 seconds, Turbo Pascal's emulator 78.0,
the 8087 30.4 (it was 30.3 before). The counters say the 8087's stores
put the epoch on not once in the run; the time is SANE's. The
polynomial's loop is some fourteen 8087 instructions a pass, five of them
multiplications at 5.8 ms: of about 38 ms a pass, 29 are SANE
multiplying. The translator speeds up the 8088 code around the 8087's
instructions, of which a Turbo Pascal program has little, and costs a
way out of the piece and back for each ESC: at 16 MHz the 8087 build
takes 93 ticks with the translator and 87 without, about 7%.

**Calling the 8087 from translated code** (the plan's last point, "only
if material") would save at most that 7%, for a template that calls into
another bank with its own data bank and gives the instruction back on an
interrupt. Not built. **What would be material is the multiplication**
(and the division): done here, as `FPREM` is, sixteen 16-bit products by
shifts and adds and IEEE's rounding, it might take a third of SANE's
16,000 cycles; the polynomial would then be about half as long, and the
8087 build ahead of `Real` with the translator as it is without it. That
is arithmetic, not the translator's, and is the next thing to measure if
the 8087 is to be faster still. It would also mean a card that speeds up
SANE is no longer used for those two operations.

## Multiply and divide done here

`fp_md` in `src/fpu/fpu.s`: a multiplication or division of two normal
numbers (both tagged valid, their integer bits set) is done by the image,
not by SANE. Anything else (an unnormal, a result that would overflow or
underflow) goes to SANE as before, which keeps the 8087's rules for
those in one place.

- **Multiply:** shift and add over the multiplier's bits into a 128-bit
  product; a zero word of the multiplier is a sixteen-bit shift, and the
  operand with more zero words is made the multiplier (a constant such
  as 0.5, an integer loaded by `FILD`).
- **Divide:** restoring division, 64 quotient bits and a guard bit, what
  is left the sticky; the subtraction starts at the divisor's first word
  that is not 0.
- **Rounding** (`fp_rnd`): to the control word's precision, 64, 53 or 24
  bits, in its direction, from the guard bit and the sticky; P raised
  here when inexact, so SANE's flags are not involved. The exponent's
  range is extended's at every precision (the 8087's), where SANE's
  precision control also narrows it.
- **Test:** `tests/com/fpumd.asm` (`tools/gen_fputest.py`), 362 cases:
  seventy pairs of random 64-bit significands multiplied and divided,
  each in one of the twelve directions and precisions, and nine pairs
  chosen for their edges (a tie at 64 bits, all-ones significands,
  integers, a quotient that rounds up to the next power of two) in all
  twelve; and the ends of the range, inside and handed to SANE. Against
  exact arithmetic, all pass, with and without the translator, in both
  layouts and under both front ends.

Measured, stock speed, 300 of each in a loop (the loop's own cost taken
out by `FADD`, which is still SANE's):

| | SANE | here | |
| --- | ---: | ---: | ---: |
| `FMUL`, two random significands | 4.7 ms | 2.8 ms | 1.65 times |
| `FDIV`, two random significands | 4.9 ms | 3.6 ms | 1.36 times |
| `FIDIV` by 7 | 3.6 ms | 3.2 ms | 1.1 times |

SANE already divides quickly by a divisor with few significant bits,
which is why the division gains least where programs divide most (by an
integer). Turbo Pascal (`tools/tp_bench.py`), the 8087 build:

| seconds | before | now |
| --- | ---: | ---: |
| the polynomial, the interpreter | 15.2 | 11.6 |
| all, the interpreter | 28.4 | 23.8 |
| all, with the translator | 30.4 | 26.6 (Real: 27.7) |

So the 8087 build is now 3.0 times as fast as `Real` under the
interpreter and a little ahead of it with the translator, and 4.4 times
as fast as Turbo Pascal's emulator. A card that speeds up SANE is no
longer used for these two operations; it is still used for everything
else.

**What would be faster still:** the multiply is shift-and-add, a bit a
time, about 7,500 cycles. Products of bytes by a table of quarter squares
(f(a+b) - f(a-b), a 1 KB table) added at their byte offsets would need no
shifting at all, and might be twice as fast; the division has no such
trick without a divide instruction.
